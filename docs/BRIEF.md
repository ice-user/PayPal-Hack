# Precedent: one-page brief (working title)

**Pitch:** an AI operations consultant for PayPal merchants. It detects a problem
(first: dispute and chargeback spikes), retrieves similar past cases, explains its
reasoning, proposes a remedy and, only after policy checks and human approval,
executes supported actions through PayPal. It then tracks the observed outcome and
adds it to the case library.

**Vision (roadmap, not scope):** the loop situation, precedent, recommendation,
approval, action, outcome is reusable. Cash flow and invoicing are future domains
on the same loop. We build and demo **one** domain end to end.

**One-line test for every idea:** does it make the precedent visibly change the
action, make PayPal more central, or materially improve trust, explainability or
safe human oversight? If not, cut or defer it.

Full design and PayPal capability notes: `docs/DESIGN.md`.

## 1. Decisions (agreed)

| # | Decision | Answer |
|---|---|---|
| 1 | Wedge | **Disputes and chargebacks.** Other finance domains are roadmap only; no generalisation layer is built |
| 2 | Demo scenario | **Item-not-received spike concentrated on one carrier and SKU.** The order and fulfilment feed is synthetic, generated by us |
| 3 | Case sources | **Hybrid:** public sources, clearly labelled authored cases, sandbox-generated cases. Every case carries provenance and `evidence_quality` |
| 4 | Real vs simulated | **Only capabilities verified in our own sandbox are used.** Real dispute reads and seller actions where they work; the outcome clock is simulated and labelled |
| 5 | Approval tiers | **Prepare-only** (drafts, analysis): AUTO. **External actions** (submit evidence, message buyer): one-click approval. **Money or claim actions** (refund, offer, accept claim): explicit approval, BLOCKED above a hard cap. All limits enforced in code |
| 6 | PayPal tool layer | **Direct REST behind a backend adapter first.** Agent Toolkit or MCP only if the core path works and it adds value |
| 7 | Cut list | **Cut by default:** fine-tuning, multi-tenant, knowledge graph, other domains. Revisit only at the 3-day checkpoint, and only if the core scenario already runs end to end |
| 8 | Evidence rule | **Numeric predicted effects only from measured cases.** Authored cases give qualitative playbook notes. Outcomes are "observed", never "caused" |
| 9 | Second demo beat | **Same symptom, three situations** (one carrier / many carriers with delays / delivered orders), three different recommendations |

## 2. The contract (do not change without telling the other person)

Two JSON shapes, defined in `docs/DESIGN.md` section 3. Keep schemas and fixtures in
`/contracts`.

- `SituationRecord`: volume, dispute rate with baseline and confidence interval,
  trend, reason mix, carrier and SKU concentration from the order feed, fulfilment
  delay, open disputes, response time, short narrative. **B produces; A's Consultant and UI consume it.**
- `Recommendation`: diagnosis, precedents with `matched_on` and `differs_on`, typed
  actions (fixed enum), predicted effect **from measured cases only**, playbook
  notes, counterfactual, confidence, evidence quality, required approval, `abstain`.
  **A produces; B's gate consumes it.**

Hard rules:
- The LLM never makes raw PayPal calls; policy, validation and execution are code.
- Credentials stay on the backend.
- Every recommendation cites its cases; the system abstains when evidence is
  insufficient or the action is unsafe, unsupported or unauthorised.
- Say "observed" or "followed", never "caused".
- Anything simulated is labelled simulated in the UI, README and video.

## 3. Two spikes, run in parallel before anything else

**Spike 1: PayPal dispute path (Person B), about 1 to 2 hours**
1. Developer account; sandbox business and buyer accounts; REST app (note client ID
   and secret); confirm the Disputes setup and scopes.
2. Make a sandbox purchase from the buyer to the business.
3. Create a dispute through the sandbox-only endpoint (`DISPUTE_CREATE` scope,
   buyer-side setup, `PayPal-Auth-Assertion` header).
4. Read the dispute back and inspect its status and allowed actions.
5. Try the seller actions the dispute allows: provide evidence, send message, make
   offer, accept claim. Note lifecycle limits and funds needed.
6. If time permits: sandbox status update or settle, and a webhook with signature
   verification.
7. Report exact working calls, setup, errors and limits. An endpoint in the docs is
   not proof our app can use it.

**Spike 2: case extraction (Person A), about 2 hours**
1. Five real sources: two FTC payment-processor cases, plus PayPal and Block 10-K
   loss disclosures (EDGAR needs a User-Agent header).
2. Fill the case schema per source: context, trigger signals with numbers,
   diagnosis, intervention, outcome (before, after, time frame), source, licence,
   `evidence_quality`.
3. Label each field directly sourced, inferred or authored. Leave gaps empty.
4. Report which fields you could fill for each case.

**Pass:** Spike 1, a dispute is created and at least one seller action works.
Spike 2, at least three of five cases support meaningfully different decisions with
provenance recorded.
**If a spike fails:** Spike 1, B drives the adapter from simulated dispute events
through the same interface, with the limit visible. Spike 2, change the source mix
or narrow the schema.

## 4. Split

| Person A: frontend and language ML | Person B: backend and retrieval ML |
|---|---|
| Whole frontend: dashboard, precedents, plan, approval flow, timeline, three-situation switcher | Sandbox accounts, PayPal adapter, webhooks (Spike 1) |
| Case library and case schema (Spike 2) | Policy Gate (three tiers), Executor, audit log |
| Consultant: prompt, typed output, abstention | API layer, database, hosting, README, licence |
| Eval: ablation rubric and scoring | Order and fulfilment generator, Situation Builder |
| Demo script and recording | Retriever, Outcome Tracker (simulated clock) |
| | Policy and execution tests, Recall@3 harness |

Handoffs: B exposes a documented HTTP API (mock responses first) that A's frontend
calls. A provides `recommend(situation, precedents)` returning a `Recommendation`,
called by B's API. Shared: `/contracts` (schemas and fixtures) and the case schema.

## 5. Ground rules

- Every case carries provenance (`public`, `authored`, `live_simulated`) and
  `evidence_quality`. Never present authored or simulated results as measured.
- The UI explains diagnosis, matched precedents, differences, uncertainty, proposed
  action, policy decision and execution result.
- Not investment advice: decision support with cited precedents.
- Repo public-ready from the start: no secrets committed, licence added.
